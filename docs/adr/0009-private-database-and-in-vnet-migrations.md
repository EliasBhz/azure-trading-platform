# ADR-0009: A database with no public endpoint, and migrations that run inside the VNet

- Status: accepted
- Date: 2026-09-15

## Context

PostgreSQL Flexible Server offers two networking modes, chosen at creation and
never changeable afterwards: a public endpoint guarded by firewall rules, or
injection into a delegated subnet with no public endpoint at all.

Schema migrations have to run somewhere. The obvious place is the deployment
pipeline, immediately before the new image is rolled out.

## Decision

The server is injected into a delegated subnet. It has no public endpoint to
disable, no firewall rule to get wrong, and its FQDN resolves only inside a VNet
linked to the private DNS zone.

The consequence is accepted rather than worked around: **nothing outside the
VNet can reach the database, including Terraform and GitHub-hosted runners.**
Migrations therefore run as a manually triggered Container Apps Job in the same
environment as the bot, using the same image, with `alembic upgrade head` as its
command.

## Alternatives considered

- **Public endpoint with firewall rules.** Rejected. GitHub-hosted runners have
  no stable egress addresses, so the allow list would either be maintained by
  hand against a published range that changes, or opened to everything. A
  firewall rule that is permanently open is worse than no firewall, because it
  looks like a control.
- **A self-hosted runner inside the VNet.** Rejected: a VM to patch, pay for and
  keep alive, to solve a problem a job already solves.
- **Migrations on application start-up.** Rejected. Two concurrent job
  executions would race on the same migration, and a failed migration would
  surface as a crashed cycle rather than as a failed deployment step.
- **A jump host or VPN for operator access.** Rejected for cost. The practical
  consequence is that inspecting the database means running a job, which is
  recorded in the runbook rather than discovered during an incident.

## Consequences

- Deployment gains an ordering constraint: image pushed, migration job run and
  succeeded, then the trading job runs. Phase 4 encodes this in CI.
- A Container Apps Job cannot be created at all until its image exists. Azure
  validates the manifest at creation time and returns `MANIFEST_UNKNOWN`, so the
  first deployment is necessarily two steps: infrastructure, push, then jobs.
  This is a property of the platform, not of this configuration.
- The database administrator password is generated by Terraform and stored in
  Key Vault, which means it also exists in the Terraform state. The state is on
  a storage account with shared keys disabled, geo-redundant and versioned,
  reachable only through Entra ID RBAC. Entra ID only authentication would
  remove the password entirely, but creating the managed identity's database
  role needs an admin connection from inside the VNet, which is another
  bootstrap job. That is the next hardening step, and it is listed here rather
  than left implicit.
- `sslmode=require` rather than `verify-full`: the certificate chain would have
  to be shipped in the image to verify it. The connection cannot leave the VNet,
  which bounds the exposure, but this is a weaker guarantee than it could be.
